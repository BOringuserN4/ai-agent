# 记忆抽取：评测与本地化评估

> 起因：想把「记忆抽取」（判断这轮值不值得长期记住）从云端 DeepSeek
> 挪到本地小模型。本文先建评测、跑出云端基线，再对比本地模型。
> 完成日期：2026/09/19。

---

## 1. 是什么

`agent/extractor.py` 的**记忆过滤器**：每轮对话结束后，判断这轮是否值得
写入长期记忆；值得的话，概括成一句话 + 打标签。

```
用户问 → Agent 答 → 【抽取器】判断 → keep=True → 写入 ChromaDB
                                  └→ keep=False → 丢弃
```

**为什么不能无脑全存**：否则「你好」「谢谢」会把记忆库塞满，检索时全是噪声。

---

## 2. 结构定位

- **谁控制流**：代码（`core.py` 里后台线程调用），不涉及 LLM 决策流。
- **信息流**：串联，位于「Agent 回答之后」与「写入向量库之前」之间。
- **任务性质**：**混合**——keep 是**分类**，text 是**生成**（要概括），tags 是**抽取**。

> 这一点很重要：任务拆开看，三个子任务适合的模型类型不同。

---

## 3. 为什么这么设计（评测部分）

### 3.1 先有尺子，再量东西

换模型前必须有评测，否则无法判断「换了是好是坏」。
**记忆抽取的错误是延迟显现的**——当时看不出来，过一阵发现记忆库歪了。

路径与 embedding 那次一致：**先建评测 → 跑云端基线 → 再让候选模型考同一套**。

### 3.2 判分原则：不用 LLM-as-judge

三个维度**全部确定性判定**（沿用本项目「能测量的别让 LLM 判」）：

| 维度 | 判法 |
|---|---|
| keep 对错 | 直接比布尔值 |
| text 质量 | 关键词覆盖（确定性） |
| tags 质量 | 集合比较 |

引入 LLM judge 只会**增加一个噪声源**，而这三项本来就能客观测。

### 3.3 keep 的两个方向分开统计（关键设计）

**漏记**（该记没记）与**误记**（不该记却记了）**严重性不同**：

- 漏记 = 丢一条信息；
- **误记 = 污染记忆库**，会长期干扰检索，且很难察觉。

所以不只看「准确率」，必须分开盯这两个数。

---

## 4. 代价（值钱那行）

| 代价项 | 说明 |
|---|---|
| **题集质量决定一切** | 题太容易 → 天花板效应，测不出差异（本次就撞上了，见 §7） |
| **期望值易过严** | tags 的期望是「命名习惯」，不是「对错」（本次也撞上了） |
| **确定性判定有盲区** | 关键词覆盖能测「有没有丢信息」，测不出「概括得好不好」 |
| **无法覆盖长尾** | 12 条题覆盖不了真实对话的多样性 |
| **云端基线非免费** | 每次跑基线都真实消耗 API（本次 36 次调用） |

## 6. 怎么跑

```bash
# 云端基线
.venv/bin/python eval_memory_extract.py --repeat 3 --save eval_reports/extract_baseline_cloud.json

# 本地模型（必须关思考，原因见 §7）
.venv/bin/python eval_memory_extract.py \
    --model "gemma4-e4b:latest" \
    --base-url "http://192.168.1.252:11434/v1" \
    --reasoning-effort none \
    --save eval_reports/extract_gemma4_nothink.json
```

## 7. 实测账（2026/09/19）

### 三组结果

| 指标 | 云端 deepseek-flash | gemma4-e4b（**开思考**） | gemma4-e4b（**关思考**） |
|---|---|---|---|
| keep 准确率 | **100%** (12/12) | **58%** (7/12) | **100%** (12/12) |
| — 漏记 | 0 | **5** | 0 |
| — 误记 | 0 | 0 | 0 |
| 概括覆盖 | 100% (5/5) | 0/0（无样本） | 100% (5/5) |
| 标签命中 | 100% (5/5) | — | **60%** (3/5) |
| 延迟（中位） | 747 ms | 3175 ms | **700 ms** |
| 3 次稳定性 | 12/12 一致 | — | — |

### ⚠️ 最重要的发现：思考模式让本地模型**从 100% 掉到 58%**

**这不是能力问题，是格式问题。** 查证过程：

```
默认（开思考）     → 返回 content = ''        （空字符串！）
reasoning_effort=none → 返回完美 JSON：
    {"keep": true, "text": "用户名叫小王，是一名测试开发工程师。", "tags": [...]}
```

**根因**：思考模式把 `max_tokens=200` 的预算**全烧在推理 token 上**，
正文一个字没剩 → 抽取器兜底为 `keep=False` → 表现为「永远不记」。

于是 5 条该记的题**全部漏记**（58% 准确率的真相是「一律说不记」）。

> **这和工具选择那次的发现是同一个原因**：小模型的「推理」不但无益，还会
> 吃掉输出预算。NuMind 的论文也报告了同一现象（小模型推理易陷入重复循环、
> 撞输出上限导致请求失败）。
>
> **结论：本地小模型必须关掉思考。** 已在 `extractor.py` 的 docstring 里写明。

### 标签质量的「失败」其实是**题集的缺陷**

看具体值：

| ID | 云端 tags | 本地 tags |
|---|---|---|
| k3 | `['fact','project']` | `['project','topic']` |
| k4 | `['personal_info','fact']` | `['personal_info','pet']` |

本地给的是 `project` / `pet` —— **比期望的 `fact` 更具体、更有用**。
它不是答错，是**命名习惯不同**。是我的期望值定得太死：
**tags 指标测的是「与我的命名习惯是否一致」，不是「标签质量」。**

### 天花板效应（题集局限）

云端在 keep 和概括上**都是 100%**，本地关思考后**也是 100%**。
这说明**题集对强模型没有区分度**。

它的正确用途是当「**下限门槛**」：
- 本地若低于满分 → 确实更差；
- 本地也是满分 → **只能说明本套题太容易，不能据此断言两者等价**。

要真正区分，需加更难的反例：如「用户提到的第三方信息」
「助手自己编的例子」「多轮后才出现的事实」。

### 延迟：这次没有明显优势

云端 747ms vs 本地 700ms——**基本持平**（云端上轮 919ms，网络抖动大）。
与 embedding 那次（81ms vs 158ms，本地快一倍）不同，**这次延迟不是理由**。

---

## 8. 结论

**目前不能断言本地更差，也不能断言等价。** 准确的表述是：

1. **关思考后，本地 gemma4-e4b 在 keep 和概括上与云端打平（都 100%）**；
2. **思考模式是致命的**——不关会让抽取器变成「什么都不记」，且**静默失败**；
3. **题集有天花板效应**，且 tags 指标设计有缺陷——**两处都需要先修**，才谈得上决策。

**下一步（按优先级）**：

1. **修题集**：加更难的用例（第三方信息、助手自造例子、多轮事实），打破天花板；
2. **修 tags 指标**：改成「标签是否与内容语义相符」而不是「与我的命名是否一致」；
3. 修完重跑，再决定是否切换；
4. 若切换：`extractor.py` 换成本地端点 + 必须带 `reasoning_effort=none`。

---

## 9. 踩过的坑

| 坑 | 说明 |
|---|---|
| **思考模式静默吃掉输出** | 返回空 content，抽取器兜底 `keep=False`，表现为「永远不记」——**不报错、不崩溃，最难发现** |
| **只看准确率会误判** | 58% 看着「还行」，实际是「5 条该记的全漏」的灾难性退化，必须分开看漏记/误记 |
| **期望值定太死** | tags 期望写成固定词表，把「更具体的标签」判成了错 |
| **题集天花板效应** | 两个模型都 100%，等于没测出差异——**评测满分不等于评测有效** |
