## 二、核心知识：一条链路，五层

这是今天最值钱的认知——**为什么"改一个地址"就能用上自己家的模型**。

```
⑤ 应用层   你的代码（OpenAI SDK）        ← 唯一动手的地方
              ↓ 只换 base_url
④ 协议层   HTTP + JSON（形状完全相同）
              ↓
③ 网络层   公网 TLS  ｜  局域网 TCP
              ↓
② 服务层   DeepSeek 集群 ｜ Ollama 守护进程
              ↓
① 硬件层   数据中心 GPU ｜ RX 7900 GRE + ROCm
```

**关键协议**：Ollama 同时暴露两套 API 面：

```
/api/*     ← Ollama 原生格式
/v1/*      ← OpenAI 兼容格式   ← 就是这一层让「零改动」成立
```

**所以真正的机制是**：

> **Ollama 实现了一次 OpenAI 协议，所有 OpenAI SDK 客户端就都能用它。**

这和你学的 MCP 是**同一个思想换了个战场**：
- MCP 解决「N 个框架 × M 个工具」= N×M 份适配；
- OpenAI 兼容 API 解决「N 个客户端 × M 个模型服务」= 同样的问题。
- 答案是同一个：**各方各实现一次协议（N+M），不要两两适配**。

**一句话收口**：

> **协议可以伪造，能力不能伪造。**
> 你的主机没有变成 DeepSeek，它变成了「一个说同样协议的服务器」。
> 请求格式、响应结构、流式输出、错误码全都一致；
> 但参数量、上下文、并发、可用性完全是另一量级。

## 三、实测数据汇总

### 3.1 embedding：本地 vs 云端

| 指标 | 云端 text-embedding-v3 | 本地 Qwen3-Embedding-0.6B |
|---|---|---|
| 延迟（中位） | 158.5 ms | **81.0 ms** |
| 该召回组分数 | 0.6787 ~ 0.8637 | 0.6321 ~ 0.8680 |
| 不该召回组最高 | 0.5154 | 0.4754 |
| 两组空档 | +0.1633 | **+0.1567** |
| 最佳阈值 | 0.60（10/10） | 0.60（10/10） |

结论：**质量持平、速度快一倍**。
旁证：同一句话在两个后端的向量 cosine = **-0.0522** → 确非同一空间，不可混用。

### 3.2 本地推理链路的开销

| 项 | 实测 |
|---|---|
| 协议层往返（跨进程） | **0.69 ms** |
| 局域网 TCP 握手 | 12 ms |
| 冷启动（拉子进程+握手+发现） | ≈500 ms |

**反直觉**：0.69ms 相对一次 LLM 调用（约 1s）是噪声。
**「协议层很贵」是错觉**——真正贵的是模型推理本身。

### 3.3 记忆抽取：三个模型对比

| 模型 | keep 准确率 | 误记 | 概括 | 标签 | 延迟中位 |
|---|---|---|---|---|---|
| 云端 deepseek-flash | **100%** (20/20) | 0 | 8/8 | 8/8 | 843 ms |
| gemma4-e4b（关思考） | 95% (19/20) | 1 | 8/8 | 8/8 | 515 ms |
| NuExtract3（关思考） | 90% (18/20) | **2** | 8/8 | 8/8 | 488 ms |
| **gemma4 + 显式规则** | **100%** (20/20) | **0** | 8/8 | 8/8 | 614 ms |

留出验证（6 条全新用例）：gemma4+规则 **6/6**｜NuExtract3+规则 6/6｜云端 6/6。

## 四、今天最值钱的五条教训

### 1. 静默失败最难发现

**现象**：本地模型开了思考模式，返回**空字符串**（推理 token 吃光 `max_tokens` 预算）
→ 抽取器兜底为 `keep=False` → **表现为「永远不记」**。

**不报错、不崩溃**，只是安静地什么都不做。如果不是我顺手跑评测，这个 bug 可能几周后才被发现。

> **教训**：小模型的「推理」不但无益，还会吃掉输出预算。**本地小模型必须关思考。**
> 这与 NuMind 论文的发现一致（小模型推理易陷入重复循环、撞输出上限导致失败）。

### 2. 只看准确率会误判

第一次跑本地模型得到 **58%**——看着"还行"。
拆开才发现：**5 条该记的，一条都没记**（"一律说不记"的灾难性退化）。

> **教训**：**失败方向比失败率重要。**
> 所以评测里「漏记」与「误记」必须分开统计——**误记会污染记忆库，比漏记严重得多**。

### 3. 专用模型 ≠ 适合你的任务

NuExtract 是**专门做结构化抽取**的模型，结果在本任务上**输给通用的 gemma4**（90% vs 95%）。

> **原因**：题目类型不匹配。
> 记忆抽取的核心是「**判断该不该记**」（分类），不是「从文本里抠字段」（抽取）。

> **教训**：选模型先看**任务性质**，不是看模型名头。

### 4. 评测满分 ≠ 评测有效

第一版题集：云端 100%、本地也 100% —— **两者都满分，等于什么都没测出来**。

加了 8 条灰色地带难例（第三方信息、助手自造内容、假设句…），差距立刻显现：**95% vs 100%**。

> **教训**：**题集的难度决定评测的价值。** 能测出差异的评测，才是评测。

### 5. 一条 prompt 规则就能修好模型缺陷

本地模型唯一丢分的行为是「把助手上轮说的话当成用户的事实存下」。
在 system prompt 里加一段显式规则后，**从 95% 升到 100%，零误记**。

> **教训**：在换模型之前，先试试**把要求写清楚**。成本近乎为零，收益却可能等同换模型。

## 五、踩过的坑（工程向）

| 坑 | 症状 | 原因 / 解法 |
|---|---|---|
| **Ollama 只绑 127.0.0.1** | 局域网连不上 | 出厂不对网络开放，需 `OLLAMA_HOST=0.0.0.0:11434` |
| **改完环境变量不重启** | 像「设了没用」 | 进程启动时读环境变量，**必须重启 Ollama** |
| **防火墙** | 端口通不了 | 放行入站 11434，且网络配置档须为「专用」 |
| **缺 AMD HIP 运行时** | 能跑但巨慢 | `amdhip64*.dll` 缺失 → **静默回落 CPU**（慢 10-100 倍）|
| （同上·查法） | — | 用 `ollama ps` 看 PROCESSOR 列是否为 `100% GPU` |
| **评测被默认参数骗** | 阈值扫描「完美」 | `search()` 默认带 `min_score=0.6` 过滤，负例被提前滤掉 → 必须显式 `min_score=0.0` |
| **`.env.bak_*` 未被忽略** | 密钥可能入库 | `*.bak` 只匹配以 `.bak` 结尾；已补 `.env.*` / `*.env.*` |
| **PowerShell 读无 BOM 脚本** | 中文乱码 | PS 5.1 按系统 ANSI(GBK) 解析，`.ps1` 需 UTF-8 **BOM** |
| **黑洞地址测超时假死** | 测试卡住 | 用 `10.255.255.1` 会等 60s×重试；改「本机未监听端口」立刻拒绝 |

## 八、一句话总结今天

> **本地化的价值不在省钱（云端一个月才 ¥0.23），而在「设计解锁」**：
> 凡是被「调用一次要花钱」劝退的设计，边际成本都变成 ≈0。
>
> **但前提是「质量不过关就不能上」**——而判断质量过关与否，
> **唯一的方法是先有一把尺子**。今天最大的产出不是那些模型，是那把尺子。
