# 本地推理：把 embedding 挪到局域网主机

> 起因：本机有一台 Windows 主机（RX 7900 GRE 16GB），想用 Ollama 跑小模型
> （embedding、工具选择），通过局域网给 Mac 上的本项目用。
> 本文记录**可行性结论、成本对比、实现方式、以及为什么核心价值不是省钱**。
> 完成日期：2026/09/19。

---

## 1. 是什么

把「调用云端 API 的小模型」，换成「调用局域网主机上 Ollama 的小模型」。

本项目**第一步只换 embedding**（记忆模块的向量化），因为它是收益最干净的那一块。

```
记忆写入/检索 → embedding 后端（可插拔）
                    ├── dashscope（云端 text-embedding-v3）  ← 现状
                    └── ollama   （局域网 Qwen3-Embedding-0.6B）
```

---

## 2. 结构定位

- **谁控制流**：代码（环境变量 `EMBEDDING_BACKEND` 决定走哪条路），不涉及 LLM 判断。
- **信息流**：串联，但在「记忆模块 → 向量化」这一步多了一个可替换的后端。
- **在系统中的位置**：只影响 `agent/memory.py` 的 `_embed()`，**不碰** Agent 循环、编排、MCP。

---

## 3. 为什么这么设计

### 3.1 硬件可行性（已核实）

| 检查项 | 结果 |
|---|---|
| RX 7900 GRE 架构 | **gfx1100**（RDNA3） |
| ROCm 7.x 官方支持 | ✅ 支持（Linux；Windows 需 ROCm v7 / HIP7 驱动栈） |
| Ollama 支持清单 | ✅ 明确列有 `7900 GRE` |
| Windows 兜底 | Vulkan 后端默认启用，没有 HIP 也能跑 GPU（性能略低） |
| 16GB 显存 | 绰绰有余（见 §5 显存预算） |

### 3.2 设计取舍：可插拔，而不是直接替换

**换 embedding 模型 = 换整个向量空间。**旧向量和新向量不可混用，
所以正确的做法不是删掉云端代码，而是让两条路并存：

- 同一套语料 + 同一套用例，分别跑两个后端，**比召回质量**；
- 质量没掉，才有理由切；
- **回滚 = 改一个环境变量**，而不是一次代码手术。

### 3.3 设计取舍：先只做 embedding，不动 Router

Router 现在用的是**规则预筛**（零成本、确定性、09-17 实测省 42%）。
把它换成本地 LLM 是「用功耗换灵活性」，**收益不明确**，所以先不做。

## 4. 代价（值钱那行）

| 代价 | 说明 |
|---|---|
| **机器得管** | 要么常开（350W × 24h ≈ ¥151/月电费），要么忍受冷启动 |
| **运维复杂度** | ROCm 驱动 + Ollama 服务 + 局域网依赖，多一层会坏的东西 |
| **质量风险** | 0.6B 的本地 embedding **未必比得上** text-embedding-v3 —— 必须实测，不能假设 |
| **单卡争抢** | 一张卡同时跑 embedding 和 router 会排队 |
| **必须留云端兜底** | 主机休眠/宕机时，Agent 不能直接死 |
| **向量空间不通用** | 两个后端的向量**不能混表检索**，集合必须隔离 |

### ⚠️ 最重要的代价：省钱这个理由不成立

用真实价格算（DeepSeek 官方定价、阿里云百炼页、上海居民电价）：

| 项 | 数值 |
|---|---|
| 每轮 embedding 用量 | ~100 token（召回查询 + 写入各一次） |
| 按 150 轮/天 × 30 天 | 450,000 token/月 |
| **云端费用** | **¥0.23/月**（¥0.5/百万 token） |
| 本地电费（按需 1h/天） | ¥6.3/月 |
| 本地电费（24h 常开） | ¥151/月 |

**云端一年才 ¥2.7。本地无论怎么算都不会更便宜。**

> 结论：**省钱不是理由**。真正的价值在 §7。

## 5. 代码在哪

| 文件 | 说明 |
|---|---|
| `agent/embedding_backends.py` | 后端抽象：`DashScopeBackend` / `OllamaBackend` + `get_backend()` 工厂 |
| `agent/memory.py` | `MemoryStore` 接受 `backend=`；collection 名**按后端隔离** |
| `eval_embedding_compare.py` | A/B 对比：同一语料用例，比召回质量 + 延迟 |
| `scripts/win_ollama_setup.ps1` | Windows 主机侧：体检 + 环境变量 + 防火墙 + 拉模型 + 验证 |
| `scripts/check_local_llm_host.py` | Mac 侧诊断：分 5 步定位「哪一层断了」 |

### 关键实现细节

1. **归一化统一在基类做**，保证两个后端相似度口径一致（cosine）。
2. **维度校验**：输出维度不是 1024 就直接报错——防止两种向量混进一张表。
3. **collection 按后端隔离**：`memory_store`（云端）/ `memory_store_ollama`（本地）。
   云端沿用原名，**不迁移、不影响既有数据**。
4. **Ollama 走 OpenAI 兼容端点**（`/v1/embeddings`），
   因为记忆模块本来就用 OpenAI SDK，换后端**调用代码零改动**。

### 显存预算（16GB）

| 项 | 占用 |
|---|---|
| Qwen3-Embedding-0.6B | 0.6 GB |
| Qwen3-4B（若日后做本地 router） | 2.6 GB |
| KV cache（8K 上下文） | ~1 GB |
| **合计** | **~4.2 GB**（16GB 绰绰有余，甚至能顺带跑 8B） |

## 6. 怎么跑

### 第一步：Windows 主机侧（一次性）

```powershell
# 以「管理员 PowerShell」运行
Set-ExecutionPolicy -Scope Process Bypass -Force
.\scripts\win_ollama_setup.ps1
```

脚本会体检 HIP 驱动、设 `OLLAMA_HOST=0.0.0.0:11434`、放行防火墙、拉
`qwen3-embedding:0.6b`，并用 `ollama ps` 验证 **GPU 真的在干活**。

> ⚠️ 默认 Ollama 只绑 `127.0.0.1`，局域网连不上——这是最容易卡住的一步。
> 而且**改完环境变量必须重启 Ollama** 才生效。

### 第二步：Mac 侧诊断

```bash
.venv/bin/python scripts/check_local_llm_host.py http://192.168.x.x:11434
```

按 5 步（TCP → 服务 → 模型清单 → embedding 实跑 → GPU 占用）定位问题，
哪一层断了会直接告诉你排查方向。

### 第三步：A/B 对比

```bash
# 先测云端基线（不需要本地主机）
.venv/bin/python eval_embedding_compare.py dashscope

# 两个一起测
.venv/bin/python eval_embedding_compare.py dashscope ollama
```

### 第四步：确认质量后切换

```bash
# 在 .env 里
EMBEDDING_BACKEND=ollama
OLLAMA_HOST_URL=http://192.168.x.x:11434
```

> ⚠️ **切换必须重建向量库**。旧向量（云端）和新向量（本地）在不同空间，
> 混用会直接崩坏检索。本项目当前记忆仅 4 条，**重建成本为零，现在切最便宜**。

## 7. 实测账

### 云端基线（2026/09/19，10 条语料 / 10 条用例）

| 指标 | 值 |
|---|---|
| 单条 embedding 延迟（中位） | **204 ms** |
| 该召回组分数区间 | 0.6787 ~ 0.8637 |
| 不该召回组最高分 | 0.5154 |
| **两组空档** | **+0.1633（可分）** |
| 最佳阈值 | **0.60**（判对 10/10，漏召 0，误召 0） |
| 完美阈值 | 0.55、0.60 |

这与 2026/09/14 的记录吻合（当时得 0.679~0.864 / 0.444~0.515 / 阈值 0.60），
说明评测本身可复现。

### 本地（待补）

> 待 Windows 主机配好后运行 `eval_embedding_compare.py dashscope ollama` 填充。
> 判定标准：**本地空档是否仍为正值且与云端接近**。
> 若本地空档明显变窄或重叠 → 质量不够，不切。

### ⚠️ 测量上的一个坑（本次踩到）

第一版对比脚本直接调 `store.search()`，而它**默认带 `min_score=0.6` 过滤**，
导致负例被提前滤掉，阈值扫描显示「0.00 就 10/10 全对」——**自证完美的假结论**。

修法：评测时必须显式 `min_score=0.0`，先拿到**未过滤的完整分数分布**，
再自己扫阈值。

## 8. 真正的价值（不是省钱）

**① 设计解锁 —— 这才是重点**

项目里有一个明确的盲区（09-17 压测发现）：

```
纯闲聊时也白挂 7 个工具 —— 规则法无法判断「这轮根本不需要工具」
```

当时没做的原因不是不会，而是**不划算**：判断一次要花钱，而它省的钱不够付它自己。

本地化之后，这个经济学变了：

> **凡是被「调用一次要花钱」劝退的设计，边际成本都变成 ≈ 0。**

可以做：每轮先本地判「需不需要工具」、本地路由、本地意图分类、本地记忆抽取……
这些**从「不划算所以不做」，变成「反正不要钱，做」**。

**② 隐私**：记忆库存的是用户偏好与个人事实，不出局域网。

**③ 离线可用**：主机在线即可用，不依赖外网 API 的可用性。

## 10. 踩过的坑

| 坑 | 说明 |
|---|---|
| **默认只绑 127.0.0.1** | Ollama 出厂不对局域网开放，必须 `OLLAMA_HOST=0.0.0.0:11434` |
| **改完环境变量要重启** | 不重启 Ollama 不生效，而且很隐蔽（像是「设了没用」） |
| **Windows 需 ROCm7/HIP7 驱动** | 没有 `amdhip64*.dll` 会**静默回落到 CPU**（慢 10-100 倍） |
| **`ollama ps` 看 PROCESSOR** | 显示 `100% CPU` 就是没吃到 GPU，别只看「加载成功」 |
| **评测必须绕开 min_score** | 否则阈值扫描是自证完美（见 §7） |
| **向量空间不可混用** | 换后端必须换 collection 并重建，否则检索静默崩溃 |
