## 先看一个实验

我造了 12 轮对话，每轮都挺长，最后再加一句“现在的新问题”。预算设成 200 token，然后看真正发给模型的 `messages` 有多大。

结果有点意外：

```text
request messages: 26
request old_est: 1973
history after trim: 4
history old_est: 169
```

预算 200，请求却是 1973；更离谱的是，第 0 轮还留在请求里。

为什么？因为代码的顺序是：

```python
messages = ...              # 先把请求拼好
self.trim_history(...)      # 再裁 history
client.chat.completions.create(messages=messages)
```

`messages` 已经是 list 副本了。`trim_history` 改的是 `self.history`，当前这次请求当然不受影响。它只是让“下一次”小一点。

这就是上下文工程的第一个坑：**你以为在管请求，其实只改了历史。**

---

## 一个请求里到底装了什么

我们平时说“上下文”，很容易只想到聊天记录。实际发给模型的东西至少有这些：

| 组成 | 里面是什么 | 通常能不能动 |
|---|---|---|
| system prompt | 角色、规则、输出格式 | 可以压缩，但别乱删 |
| tool schema | 工具名、参数、描述 | 不能随便裁，裁错会漏工具 |
| memory | 召回的长记忆 | 可以少注入，但别硬塞 |
| history | 过去的 user / assistant / tool | 主要裁剪对象 |
| 当前问题 | 用户这次说的话 | **不能丢** |
| output reserve | 留给回答的 token | **先扣掉** |

可以把模型窗口想成一张桌子。桌子就这么大，system、工具说明、记忆、历史、当前问题都要往上放，还得给回答留一块地方。历史放多了，回答就没地方；硬塞，API 直接报超限。

所以预算应该这么算：

```text
input_budget   = context_window - output_reserve
history_budget = input_budget
                 - system_prompt
                 - tool_schema
                 - memory
                 - current_user
```

举个例子，数字只是示意：

| 项 | 示例 |
|---|---:|
| 模型窗口 | 64,000 |
| 留给回答 | 4,000 |
| system prompt | 1,200 |
| 工具说明 | 2,300 |
| 记忆 | 800 |
| 当前问题 | 300 |
| 历史还能用 | 55,400 |

很多项目只用一个 `max_tokens` 同时表示“输入预算”和“输出预算”，这两个东西其实不是一回事。输入被历史吃光，输出就会截断；输出预留太大，历史又没地方放。后面最好拆成两个参数，这次先不展开。

## 三件容易忽略的事

### 第一件：预算管的是这次请求

这个坑前面已经看到了。判断标准很简单：

> 你裁完以后，真正传给 `client.chat.completions.create` 的那份 `messages`，有没有变小？

如果变小的是 `self.history`，但 `messages` 还是旧的，那就是没生效。

`messages` 是 list 的浅拷贝，`trim_history` 里 `self.history.pop()` 不会自动改到它。这个细节很不起眼，但会让整个预算机制形同虚设。

### 第二件：一轮对话要整块处理

一条正常的工具调用大概长这样：

```text
user → assistant(tool_calls) → tool(result) → assistant
```

这四步是一轮。你可以整轮保留，也可以整轮丢掉，但不能把中间的 `assistant.tool_calls` 删了、留下 `tool`。

我拿旧实现试了一下，预算调到 101 时，history 变成了：

```text
system, tool, assistant
```

`tool` 还在，但它的 `tool_call_id` 已经找不到对应的 `assistant.tool_calls`。真实 API 会直接报错；本地 stub 可能不报，但语义已经坏了。

所以裁剪的单位不是“一条 message”，而是“一个完整的 turn”。

### 第三件：token 别估得太乐观

旧代码里写的是：

```python
# 中文约 1 字≈1 token
return max(1, len(text) // 2)
```

注释说中文 1 字 1 token，代码却按 2 字 1 token 算，直接少估一半。它还没算 `tool_calls.arguments`，也没算角色和结构开销。

我拿同一段 32 字的中文试了一下：

```text
旧版：16
新版：30
```

新版也不保证和真实 tokenizer 一模一样，但方向是“宁可高估，不要低估”。低估的后果是请求超限；高估的后果只是早一点裁。

## 历史太长，能怎么办

常见的有四种办法，不是互斥的，可以组合。

| 办法 | 做什么 | 适合什么情况 | 代价 |
|---|---|---|---|
| Drop | 丢掉最旧的完整 turn | 旧信息确实不再需要 | 早期事实会丢 |
| Summarize | 把旧 turn 压成摘要 | 旧信息还有用，但不需要原文 | 多一次调用，摘要会漂移 |
| Retrieve | 按当前问题召回旧信息 | 信息多、按需使用 | 需要索引，可能漏召回 |
| Spill | 大结果落盘，只留头尾/句柄 | 日志、堆栈、长文档 | 需要工具能再读 |

最容易踩的坑是“只靠 Drop”。

比如第 1 轮用户说：“我的职业是测试开发工程师。”第 10 轮问：“根据我的职业，帮我改简历。”如果第 1 轮被丢掉，模型不是不聪明，是它根本没看到。这个时候应该用摘要或检索，而不是继续调 prompt。

反过来，如果一条工具结果有十页日志，也没必要全塞进上下文。留头尾、写到文件里、给模型一个路径，需要时再读，通常更划算。

`ai-agent` 里其实已经有这些雏形：

- `trim_history` 是 Drop；
- `truncate_tool_output` 是截断/Spill；
- `MemoryStore` 是 Retrieve；
- 还没有真正的摘要压缩。

## 原来的代码问题在哪

问题集中在三个地方。

### `run()` 的顺序

旧版在循环外先拼了一次 `messages`，循环里又拼一次，然后才 `trim_history`。裁完 history，`messages` 没重新构建，所以当前请求还是旧的。

我把它改成了先裁、再拼：

```python
budget = self.trim_history(max_tokens)
messages = [{"role": "system", "content": self._base_system}]
if memory_context:
    messages[0]["content"] += "\n\n" + memory_context
messages.extend(budget.messages[1:])
```

这样才叫“用预算后的结果构造请求”。

### `trim_history()` 的算法

旧版从最旧的一条 message 开始 pop，不按 turn 分组。它也不检查 tool 配对，所以会出现前面那种孤儿 `tool`。

现在 `trim_history` 只做一层薄包装，真正的逻辑在 `fit_to_budget()` 里：

- 保留 system；
- 从最旧的完整 turn 开始丢；
- 至少保留最新一个 turn；
- 最新 turn 自己就超预算时，返回 `overflow=True`，不拆配对。

### `json_mode.py` 也有同样的问题

它旧版裁的是外层 `agent.history`，而且 `messages` 已经先构建了。等于既裁错了对象，又裁晚了。现在改成先裁 `json_agent.history`，再用 `budget.messages` 拼请求。

## 新预算器怎么工作

核心在 [`agent/context_budget.py`](../../agent/context_budget.py)。

几个函数分工很简单：

| 函数 | 做什么 |
|---|---|
| `estimate_text` | 估算一段文本的 token |
| `estimate_message` | 算 content + tool args + 结构开销 |
| `group_turns` | 把 history 分成 system + 完整 turn |
| `check_tool_pairing` | 检查孤儿 tool / 缺失 tool |
| `fit_to_budget` | 请求前裁剪，返回 `BudgetResult` |

`BudgetResult` 里有裁剪后的 `messages`、估算 token、保留/丢弃的 turn 数、是否 overflow，以及 tool 配对问题。

这里有个取舍：**最新 turn 自己超预算时，不硬裁。**

比如预算 101，但最新一轮工具调用本身就要 104 token。你能做的不是把 `assistant.tool_calls` 删掉，而是：

1. 返回 `overflow=True`；
2. 让上层决定摘要、截断工具结果，或者换更大预算；
3. 至少保证当前问题和 tool 配对是完整的。

“超预算但结构正确”，比“刚好不超但结构坏了”要好。

## 还没解决什么

这次只把“请求级预算 + 完整 turn + 配对”做对了。还有几块没动：

- **output reserve 还没扣**。现在 `max_tokens` 主要还是输入侧预算，没有给回答留固定空间。
- **tool schema 没算进预算**。工具多的时候，schema 本身也占不少 token。
- **overflow 只记录，没有策略**。还没有摘要、压缩、截断工具结果这些动作。
- **记忆注入只做了粗略扣减**。`memory_tokens` 是估的，不是精确值。

这些不是“忘了”，是下一步。先把预算器做对，再谈摘要，否则后面测出来的结果都不可信。

## 几个常见误解

**“历史越长，模型越懂。”**
不一定。无关历史会稀释当前问题，还会更贵、更慢。模型看的是这次请求里有什么，不是你以为它记得什么。

**“截断就是压缩。”**
截断会丢原文，摘要会丢细节，两者都不是无损的。关键信息要留可回查的原文，比如写到文件里。

**“token 按字数除以 2 估就行。”**
中文会低估一半，tool args 还没算。估少了，请求就超；估多了，只是早裁。

**“删最早一条 message 最安全。”**
如果那条是 `assistant.tool_calls`，后面的 `tool` 就成了孤儿。按 turn 删，别按条删。

**“摘要不会丢东西。”**
摘要一定丢细节。它能保留 gist，但不能替代原文。重要事实要么留在最近 turn，要么能检索回来。

---

## 最后

上下文工程听起来像“压缩历史”，实际做的是一道取舍题：

> 这次请求里，哪些信息最影响当前决策？

预算只是约束，turn 是裁剪单位，摘要/检索/落盘是不同信息寿命对应的工具。把这三件事分开，代码就不会写成“删几条 message 试试”。

这次改完，至少不会再出现“预算 200、请求 1973”的情况。下一步可以安心做摘要和早期事实实验了。
