# 编排四模式讲义

> 本项目已落地的 4 种编排模式，用**同一套框架**逐个拆解：
> 是什么 → 结构定位 → 为什么这么设计 → **代价** → 代码在哪 → 实测账。
> 配套代码：`agent/multi_agent.py`（Router / Fan-out）、`agent/pipeline.py`（Pipeline）、
> `agent/evaluator_critic.py`（Evaluator-Critic）。收口日期：2026/09/16。

---

## 0. 先立坐标系：两个轴定位一切结构

| 轴 | 取值 |
|---|---|
| **谁控制流** | 代码写死 / LLM 动态决定 |
| **信息怎么流** | 串联 / 分发-汇聚 / 广播 |

10 种编排模式都是这两个轴上的一个点。**背模式没用，会定位才有用。**

| 模式 | 谁控制流 | 信息怎么流 |
|---|---|---|
| Router | LLM | 分发-汇聚（可能只有 1 路） |
| Pipeline | **代码**（固定顺序） | 串联 |
| Fan-out / Fan-in | LLM 决定切分 | 分发-汇聚 |
| Evaluator-Critic | **代码**（固定循环） | 串联 **+ 回环** |

**一条贯穿全篇的铁律**：多 Agent 不是能力升级，是**成本结构**。
每拆一个 agent 就多付「交接损耗 + 压缩后的上下文 + token」，
必须换回某个单 agent 拿不到的东西（四条判据，见 §5）。

## 1. Router（路由）

**是什么**：一个轻量调度者先看懂请求，再决定「拆不拆、拆给谁」，自己不干活。

**结构定位**：谁控制流 = **LLM**；信息流 = 分发-汇聚。

**为什么这么设计**
用户的问题五花八门，但不需要为每种问题各写一段 if-else。
把「该怎么处理」交给 LLM 判断，规则一变只改 prompt，不动代码——
这就是「LLM 控制流」相对「代码写死」的价值：**灵活**。

**代价（值钱那行）**
- **判断本身要花钱**：实测每次路由约 **853 token**（见 §6）。任务越简单，这笔钱占比越高；
- **判断会错**：本项目最早就是被它坑的——把「算数 + 查天气」当成「跨域」拆给两个专才，
  而那两位各只有半个工具集，于是**各漏答一半**。根因不是任务属性，是**调度策略把「跨域」当成了判据**；
- 所以现在 prompt 里写死「**不确定就选 solo（不拆）**」，并给四条判据（§5）。

**代码在哪**：`agent/multi_agent.py` 的 `MultiAgent.router` + `_plan()`。

**怎么跑**
```bash
.venv/bin/python main.py        # 直接对话，Router 自动判断
```

## 2. Pipeline（流水线）

**是什么**：多个 Agent 按**固定顺序**串起来，**上一步的输出 = 下一步的输入**。

**结构定位**：谁控制流 = **代码写死**；信息流 = **串联**。

**为什么这么设计**
有些任务天然有先后依赖（先计算 → 再总结；先调研 → 再成稿），
顺序是**确定的**，不需要 LLM 每次重新决定——那就交给代码，省掉一次判断的钱，
而且**可复现**（同一输入永远同一条路径）。

关键基础设施是**结构化输出**：中间状态是 dict，下游 Agent 直接拿字段，
而不是去猜上游的自然语言在说什么（详见 `agent/json_mode.py`）。

**代价（值钱那行）**
- **流程定死 → 偏离预设就卡住**，没有反思/重规划兜底；
- 链路越长，**误差累积**（第一步小错被后面几步放大）；
- 每一步都要过一遍完整上下文，**token 随步数线性增长**。

**代码在哪**：`agent/pipeline.py`（`PipelineStep` + `Pipeline`）。

**怎么跑**
```bash
.venv/bin/python main.py
  /pipe math_to_summary 99的平方     # 计算 → 一句话总结
  /pipe research_to_report AI Agent  # 调研 → 报告
  /pipe list
```

## 3. Fan-out / Fan-in（分发-汇聚）

**是什么**：把一个任务**切分**成若干独立子任务，分发给多个专家，最后**汇聚**成一段连贯回答。

**结构定位**：谁控制流 = **LLM**（Router 决定怎么切）；信息流 = **分发-汇聚**。

**为什么这么设计**
当任务能被切成**互不依赖**的多块时，可以并行做、也可以各自用专属上下文，
避免「一个专家揣着全部背景、哪个都不精」。

**关键设计取舍：真·Fan-out ≠ 群发**
本项目最早的做法是「把整道题群发给多个专家」，结果三个坑全踩：
重复回答、越权心算、自相矛盾（各说「这半不归我管」）。
现在的做法是**先切分**：每个专家只收到**自己的那部分子任务**（`_plan()` 返回 `subtask`），
再由 `merger` 归并——归并员只能使用给定信息，不许新增、不许自行计算。

**代价（值钱那行）**
- **交接要压缩上下文 → 丢信息**：子任务切得越细，归并时越容易丢掉跨块的隐含关联；
- **归并员本身也是一份钱**（实测 771 token）；
- **当前是串行 `for` 循环**：判据②「真并行」**从未真正成立**——省的是认知负担，不是墙钟时间。

**代码在哪**：`agent/multi_agent.py` 的 `run()`（分发）+ `_merge()`（汇聚）。

**实测账（同一道「算数 + 查天气」）**

| 方案 | token | 质量 |
|---|---|---|
| 拆 2 专家 + merge（改造前） | 3624 | 完整（但重复/越权风险） |
| Router 判「不拆」→ solo（改造后） | 2242 | 完整 |
| 无 Router，直接单 Agent（理想值） | 1347 | 完整 |

## 4. Evaluator-Critic（生成-批判-重做）

**是什么**：让「生成」和「评判」由**两个不同立场**完成，不达标就带着批评重做，直到过线或封顶。

**结构定位**：谁控制流 = **代码**（固定循环 + 轮次封顶）；信息流 = **串联 + 回环**。

**本项目第一个「监督关系」**：前三种都是平级分工，这个是**一个角色管另一个角色的质量**。

**为什么批判者必须独立（判据③）**
让生成者自己批自己（self-critique）会撞上**自我确认偏差**：
它刚做完推理，满脑子都是「我这么选是有道理的」，再让它挑错会倾向于**辩护**而非找漏洞。
所以批判者要是**另一个立场**——它的职责就是找茬，找不出毛病算失职。

> ⚠️ 关键是「**立场独立**」，**不是「必须两个 Agent 实体」**。
> 同一 Agent 换一套批判人格 + 清掉生成时的上下文，也算独立立场（省一半钱）；
> 但「同一个 Agent 原地加一句『你再检查一遍』」不算，那还是自我确认偏差。

**分数怎么算（代码定规则，裁判只提供事实）**
- 硬性要求不合规 → **一票否决，封顶 59**（沿用 `judge.py` 的 must_have 思路）；
- 合规后，60-100 分由裁判给的三个「手艺分」（场景绑定 / 差异化 / 语感节奏，各 0-10）**加权折算**；
- **阈值和加权都是人的决策**，裁判只当测量仪——换题不改口径，分数才可比。

**代价（值钱那行）**
- **每重做一轮 ≈ 多付一份生成的钱 + 一份批判的钱**；
- **及格线是根旋钮**（实测见下）：拧太高会诱发「为凑分牺牲硬约束」的**反向退步**；
- 循环**必须由代码封顶**，否则「不达标就重做」是个无底洞。

**代码在哪**：`agent/evaluator_critic.py`；实验脚本 `eval_evaluator_critic.py`。

**怎么跑**
```bash
.venv/bin/python main.py
  /ec demo    # 正例：硬约束文案（能挑错，也能改好）
  /ec bad     # 反例：缺信息（命中否决线④，批了也没用）
  /ec <任意任务>

.venv/bin/python eval_evaluator_critic.py            # 正例 + 反例对照
.venv/bin/python eval_evaluator_critic.py --strict   # 追加「及格线 90」实拍
```

**实测账**

| 场景 | 轮次 | 分数轨迹 | token | 结论 |
|---|---|---|---|---|
| 正例 · 硬约束文案（线 85） | 3 | 84 → 84 → 85 | 14865 | 收敛，重做把分数推上去了 |
| 反例 · 缺信息（否决线④） | 3 | 59 → 59 → 59 | 9437 | 走平，**批了也改不动** |
| 追加 · 及格线拧到 90 | 3 | 84 → 87 → 59 | 24211 | **回退**：为凑手艺分把硬约束写崩 |

## 5. 四条判据（决定「值不值得拆」）

满足**任意一条**才值得把任务拆给多个 Agent：

1. **上下文隔离**：两个子任务需要的知识/工具互相干扰，混在一起会互相误导；
2. **真能并行**：子任务互相独立，且并行能**显著省墙钟时间**；
3. **需要不同视角**：如 evaluator 要「批判」人格，与「生成」人格天生冲突；
4. **单 Agent 装不下**：任务大到超出上下文窗口。

**「跨域」不在此列**。不满足就不该拆——拆了就是纯负债。

### 四条否决线（决定「这条任务该不该上循环」）
Evaluator-Critic 这类循环，踩任意一条就别做：
- ✗ 有客观、可程序验证的标准（能跑测试/能算）→ **用代码验证**，别雇 LLM 评委；
- ✗ 评判标准说不清（「够不够有感染力」）→ 打分漂移，重做没有方向；
- ✗ 任务便宜、单次就够 → 多一轮 ≈ 多付一份生成的钱；
- ✗ **无法从批判中改进**（缺的是信息，不是做得好不好）→ 批十遍也变不出新信息。

## 6. 实测账汇总（2026/09/16 复测）

| 模式 | 用例 | token | 耗时 | 备注 |
|---|---|---|---|---|
| Router | 「算 123×456 + 上海天气」 | **853** | — | **仅判断就要 853**，任务越简单越不划算 |
| Router 判不拆 → solo | 同上 | 1360 | 4.9s | 合计 2213 |
| Pipeline（2 步） | 「99 的平方」→ 总结 | 2650 | 2.7s | math 798 + summary 1852 |
| Fan-out（拆 2 专家） | 「算数 + 查天气」 | 3624 | — | 改造前；判不拆后降至 2242 |

### 三条结论
1. **连「不拆」这个决定本身都要花钱**——Router 每次 853 token，是判断税；
2. **能省钱的办法是把控制权交给代码**：Pipeline 固定顺序、Evaluator-Critic 固定循环，都不需要 LLM 判断；
3. **每个模式的代价都不一样，且都可测量**——写不出代价，就说明还没搞懂边界在哪。

## 7. 学习顺序（与大纲一致）

```
1. Router           → 你已经会了（核心章）
2. Pipeline         → 线性工作流，理解「结构化输出是基础设施」
3. Evaluator-Critic → 质量提升，理解「监督关系」与判据③
4. Fan-out / Fan-in → 并行加速，理解「真并行 vs 串行」
5. Planner-Executor → 复杂任务（未做）
6. Hierarchical     → 生产级（未做）
7. 其余高级模式按需
```

**先掌握 Router + Pipeline + Evaluator-Critic 三种，覆盖 80% 场景。**
