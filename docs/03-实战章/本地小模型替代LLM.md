# 专题 · 本地小模型替代 LLM：以记忆抽取为例

> 这不是“记忆怎么写”的主线，而是一个独立的模型选型专题：
> **哪些 LLM 的活可以交给本地小模型？怎么判断能不能切？**
> 主线见 [写侧：抽取什么、怎么抽](记忆抽取.md)。

---

**一句话**：本地小模型不是“更便宜的 LLM”，它只适合任务边界清楚、输出可验证、失败可兜底的活。
**适读**：想降本、降延迟、做离线，但不想把系统切坏的人。
**相关讲义**：[写侧：抽取什么、怎么抽](记忆抽取.md)、[把 embedding 挪到局域网](../99-番外/本地推理.md)

> **打个比方**：本地小模型像一把专用螺丝刀。
> 拧对应的螺丝很快，但不能拿它当瑞士军刀。

> **前情提要**：写侧需要一个“判断这轮值不值得记”的抽取器。
> **本章只回答**：这个抽取器能不能从云端 LLM 换成本地小模型？怎么判断？
> **读完后你能**：判断一个任务适不适合本地小模型，并设计一个可回退的切换方案。
> **下一章为什么存在**：模型选型只是手段；写侧的主线仍然是“记什么、怎么评”。

## 1. 为什么想本地化

把抽取器放本地，动机通常有三个：

- **钱**：每次抽取都调云端，量大了不便宜；
- **延迟**：本地少一次网络往返；
- **隐私/离线**：对话内容不出局域网。

但“LLM 的活”不是一个任务，是一包任务：
分类、抽取、概括、判断、开放式生成……
它们对模型的要求完全不同。

所以问题不是“本地模型能不能代替 LLM”，而是：

> **这一个具体的活，适不适合本地小模型？**

---

## 2. 先选任务：什么活适合小模型

| 适合 | 不适合 |
|---|---|
| 标签明确、输出 schema 固定 | 开放式生成、需要广世界知识 |
| 可以确定性判分 | 只能靠人/LLM 主观打分 |
| 高并发、低延迟、重复量大 | 一次错就不可逆 |
| 失败可兜底、可回退云端 | 没有兜底，错了也发现不了 |

记忆抽取正好是混合任务：

- `keep` 是**分类**（该不该记）；
- `text` 是**生成**（压成一句话）；
- `tags` 是**抽取**（打标签）。

所以它不是一个“纯抽取”任务。
这一点后面会变成一个反直觉的结论。

---

## 3. 实验设计：拿记忆抽取开刀

做法和 embedding 那次一样：

1. 先建评测：20 条用例，其中 8 条是难例；
2. 跑云端基线：`deepseek-flash`；
3. 让本地模型考同一套题；
4. 三个维度全部确定性判分：`keep` / `text` / `tags`。

难例专攻灰色地带：

- 第三方转述：“我朋友张三说他去日本出差了”；
- 助手自造内容：“上一轮你提到过 Langfuse…”；
- 假设句：“假设我是刚入行的前端工程师”；
- 临时状态：“我有点困”。

关键指标不是总准确率，而是：

> **误记**（不该记却记了）和**漏记**（该记没记）分开看。

---

## 4. 三轮结果

### v1：12 条题，100% vs 58%

第一版题集只有 12 条，结果很反直觉：

| 指标 | 云端 | 本地 gemma4（开思考） | 本地 gemma4（关思考） |
|---|---|---|---|
| keep | 100% | **58%** | **100%** |
| 漏记 | 0 | **5** | 0 |
| 延迟中位 | 747ms | 3175ms | 700ms |

58% 的真相不是“能力差一点”，而是**本地模型什么都没记**。

根因：开思考后，`max_tokens=200` 全被推理 token 吃掉，
返回的 `content` 是空字符串；抽取器兜底为 `keep=false`，
表现为“永远不记”。

> **结论：本地小模型做这种短输出任务，必须关思考。**
> 推理不但无益，还会吃掉输出预算。

关思考后 keep 100%，但又撞上两个评测问题：

- tags 只有 60%，因为本地给的 `project`/`pet` 比期望的 `fact` 更具体——
  这不是错，是**命名习惯不同**；
- 云端和本地都 100%，**题集太简单，没有区分度**。

### v2：20 条题，100% vs 95%

加 8 条难例、把 tags 改成“语义相符”后，差距才出来：

| 指标 | 云端 | 本地 gemma4（关思考） |
|---|---|---|
| keep | **100%** (20/20) | **95%** (19/20) |
| 漏记 | 0 | 0 |
| **误记** | **0** | **1**（h2 助手自造内容） |
| 延迟中位 | 843ms | **515ms** |

唯一丢分是 h2：

```text
本地：keep=True, text="Langfuse 是一个 LLM 可观测性平台…"
云端：keep=False（正确跳过）
```

单独复现 5 次，本地 **5/5 都误记**——这不是噪声，是系统性缺陷。

为什么这比漏记严重：

> 它会把**助手上轮说的话**当成“用户的事实”存进长期记忆。
> 以后回答就会出现“你之前提过 Langfuse”这种**凭空归因**，
> 用户很难第一时间发现。

### v3：NuExtract3 更差，显式规则把 gemma4 拉回 100%

两条改进路线：

- **B**：换更强的本地模型（NuExtract3，4.3B，Qwen3.5 基座）；
- **A**：在 prompt 里加显式规则。

B 的结果反直觉：

| 模型 | keep | 误记 |
|---|---|---|
| 云端 | 100% | 0 |
| gemma4（关思考） | 95% | 1 |
| **NuExtract3（关思考）** | **90%** | **2**（h2、h3） |

NuExtract 是专做结构化抽取的模型，却在这道题上不如通用 gemma4。
原因是**题目类型不匹配**：

> 记忆抽取的核心是“判断该不该记”（分类/判断），
> 不是“从文本里抠字段”（抽取）。
> **专用抽取模型 ≠ 适合判断任务。**

A 的结果成功。在 system prompt 里加一条规则：

```text
只记录用户本人透露的稳定信息。以下一律不记：
- 助手自己说过的话、助手提供的知识
- 用户转述的第三方信息
- 假设、比喻、举例
- 临时状态与时效数据
```

| 模型 | 加规则前 | 加规则后 |
|---|---|---|
| 云端 | 100% | 100%（不退化） |
| gemma4 | 95%（1 误记） | **100%（0 误记）** |
| NuExtract3 | 90%（2 误记） | 95%（1 误记） |

规则是照着失败用例写的，有过拟合风险。
用 6 条全新留出用例验证：三组都是 **6/6**，未见退化。

### 但切换前，必须先加 failover

抽取器现在的异常处理是：

```python
except Exception:
    return {"keep": False, ...}   # API 失败 → 静默不记
```

一旦切到本地，**那台主机关机 = 记忆功能静默停摆**：
不报错、不崩溃，只是什么都不记。

所以正确顺序是：

> **先给抽取器加 failover（照搬 embedding 的做法）→ 再切本地。**

---

## 5. 五个结论

1. **思考模式会吃输出预算**：短输出任务必须 `reasoning_effort=none`；
2. **专用抽取模型 ≠ 适合判断任务**：先看任务类型，再看模型标签；
3. **误记比漏记严重**：看失败方向，不只看准确率；
4. **显式规则能修系统性问题**：但要拿留出集验证，防止照题写规则；
5. **切换前先做 failover**：否则本地故障会变成静默停摆。

---

## 6. 什么时候该切 / 不该切

| 该切 | 不该切 |
|---|---|
| 任务边界清楚、输出可验证 | 开放式生成、模糊判断 |
| 量大、延迟/隐私收益明显 | 量小，省不了多少 |
| 有确定性评测和留出集 | 只能靠感觉判断好坏 |
| 有 failover，坏了能回云端 | 没有兜底，错了也发现不了 |

回到记忆抽取本身：

- 它跑在后台线程，**延迟对用户不可见**；
- 本地只快 300ms 左右，收益有限；
- 多一个依赖、多一条静默失败路径。

所以**纯从工程稳妥出发，保持云端也是合理选择**。
本地化不是“更先进”，只是一个有条件的选项。

---

## 7. 回到主线

本地模型选型是**实现选择**，不是记忆的主线。

记忆的主线仍然是：

- 写侧：什么值得记、怎么评（[写侧：抽取什么、怎么抽](记忆抽取.md)）；
- 读侧：怎么召回、阈值怎么定（[记忆召回修复](记忆召回修复.md)）；
- 端到端：答案有没有变（[记忆用例评测](记忆用例评测.md)）。

选型可以换，红线不能换：
> **宁可少记，不可记错。**
